# RE-001 — Product, UX and Engineering Handoff (v0.6.1 → v0.6.2)

**Purpose:** Preserve the why, the working reference experience, outstanding debt and execution order before implementing v0.6.2.

## Product thesis

The product is an **execution strategy optimizer** for enterprise AI workflows. An operator must know whether switching execution methods (premium/economy model or deterministic code) improves **fully loaded cost per verified successful outcome** without losing quality, safety, reliability or required escalation. This is not a general workflow builder or a cosmetic observability dashboard.

## Primary persona

AI platform / enterprise AI operations engineer managing an instrumented workflow. Secondary audience is technical FDE interview reviewers. User value is the credible decision process, not a large menu of enterprise features.

## Signature interaction

**Select a failing case → inspect its observed routing decision → compare baseline and candidate → revise a bounded rule → rerun matched evaluation → review eligibility → simulate exact-revision activation → verify and restore.**

All relevant context should stay in one workspace. Graph, evidence table and inspector are synchronized projections of authoritative data. The change proposal is the organizing object.

## Information architecture

- Workbench as home, with Inspect, Design change, Compare, Release as modes.
- Attention and History as drawers or contextual panels.
- Case explorer (left), interactive React Flow/ELK graph (center), decision inspector/policy editor (right), evidence dock (bottom).
- Read-only topology with clickable nodes/edges; policy edits through typed controls.
- Selected case, node/edge, proposal revision and evaluation run remain stable across modes.

## Frontend architecture recommendation

Next.js + React + TypeScript; @xyflow/react (named ReactFlow import, v12), ELK.js layout, Zustand for shared selection, Tailwind for tokens/layout, Radix/shadcn for accessible controls, react-resizable-panels, TanStack Table for case evidence, Zod for boundary validation, Motion for restrained transitions, Vitest for domain logic, Playwright for browser acceptance. Use libraries where they materially solve a real problem; don't add packages just for the sake of a stack.

**Known defect:** v0.6 originally used a default ReactFlow import and crashed. Fixed with named import. Prevent recurrence with clean production build and Playwright render test.

## Existing prototype evidence and limits

User screenshots of v0.6.1 show interactive branched topology, enlarged nodes, routing preview, selected case, inspector, and expanded paired-case table. The synthetic baseline is shown as 80/100 verified automated outcomes, with 20 correct escalations and modeled total cost $41.98 in earlier views. These are synthetic fixture figures, not production savings or a verified provider benchmark. Current preview displays reference-category routing counts; this must not be confused with runtime-observed classifier outputs.

The prior v0.6.1 delivery reported 7/7 evidence tests and TSX syntax/ZIP checks, but **did not verify full Next.js build or browser QA**. Do not claim it did.

## Design refinements already requested

1. Make graph legible, properly fit within canvas and central to the experience.
2. Node/edge selection reveals actionable evidence.
3. Compare becomes signature interaction, not just a changed side panel.
4. Rule editing updates projected routes immediately.
5. Evidence dock becomes real case-level table/detail surface.
6. Improve visual hierarchy, typography, selection and purposeful color.

The v0.6.1 screenshots suggest progress on 1, 4, 5, 6. Items 2 and 3 still require domain-level evidence. Graph fit needs further correction.

## Non-negotiable integrity principles

- Runtime-observed fields are separate from evaluation truth.
- Every aggregate comes from attributable records; no decorative shares.
- Frozen exact policy revision is tied to the evaluation that permits release.
- Inconclusive or failing candidates cannot be activated.
- Preview ≠ evaluation ≠ post-release verification.
- Restoration is auditable; historical records are not rewritten.
- Real/provider-measured claims are prohibited in synthetic-only mode.

## Build order and stop conditions

F1 evidence model → F2 rule evaluator → F3 synchronized graph/case evidence → F4 matched evaluation → F5 local release/restore → F6 independent QA. Stop when evidence provenance or a gate fails; do not mask it with visual polish. Each slice should have tests and reviewer evidence.
